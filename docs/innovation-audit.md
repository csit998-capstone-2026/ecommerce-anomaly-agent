# 五个算法模块的创新性与证据审计

本文件审计的是**电商经营异常诊断系统相对本项目普通 Agent 基线的算法改进**，不是对学术首创性的鉴定。演示范围为单店、单 SKU、指定的销量下降时段；业务观测和标注均为合成数据。原因分数用于排序，不能解释为因果概率。现有代码与实验能够证明部分机制在指定案例上的行为，不能自动证明现实店铺效果，也不能仅凭仓库文件证明五位成员各自的个人原创贡献。

## 证据边界

- 本项目的实现位置为 `src/algorithms/`，集成入口为 `src/agent/diagnose.ts`，评测代码为 `eval/modules-1-3.ts`、`eval/modules-4-5.ts`。下表数字来自本地 `runEvaluation(false)` 的只读聚合运行；原标为 `holdout` 的合成案例已被用于开发调试，**不再是未接触的盲测集**。提交报告前应对最终源码重新运行评测并保存源码版本与结果，另备独立案例做最终验证。
- 模块 1～3 的基本机制已有公开工程实现作为先例：依赖图调度与局部修复见 [Craft Agents TaskRunner 源码](https://github.com/craft-ai-agents/craft-agents-oss/blob/main/packages/server-core/src/tasks/TaskRunner.ts)，密度感知工具结果处理见 [large-response 源码](https://github.com/craft-ai-agents/craft-agents-oss/blob/main/packages/shared/src/utils/large-response.ts)，工具调用前的多阶段检查见 [pre-tool-use 源码](https://github.com/craft-ai-agents/craft-agents-oss/blob/main/packages/shared/src/agent/core/pre-tool-use.ts)。这些链接说明“已有先例”，不证明本项目逐行复用了上游代码；若要主张具体代码来源或个人作者身份，还需分别核对提交记录与许可证义务。
- “在本项目中实现或组合了改进机制”“相对普通 Agent 基线有收益”“学术首次提出”“某成员独立原创”是四种不同主张。前三项的现有实验只支持前两种主张在限定场景内成立；第四种主张必须另有个人提交、设计记录和答辩证据。

| **1 依赖图调度与局部修复**（Yan Zhuo） | 诊断任务按先进先出、最多两项并行执行；一次核验失败后整张任务图重跑。 | `scheduler.ts` 校验依赖图与环；只调度依赖完成的节点，按异常严重度、下游影响数和成本排序；失败时沿下游依赖求需重跑集合，保留其他节点结果。 | 48 个固定任务／故障模拟中，按现有执行器 `Promise.allSettled` 批次语义模拟，相对“并行 FIFO＋整图重跑”，平均完成时间为 **872.08→678.75 虚拟毫秒**，平均任务执行次数 **8.75→7**；其中 **2 例**完整方案耗时反而较长。 | 依赖图或局部重跑由本组首次发明；虚拟耗时等于真实工具／模型端到端时延；这组小图证明复杂生产任务均更快。 |
| **2 动态上下文预算**（Yan Han） | 以每四字符约一 Token 的固定估算，按原顺序保留或截断工具结果。 | `context-budget.ts` 对高密度文本与中日韩字符使用不同估算；根据**配置的**上下文窗口和预留量给出结果预算；先为销售、缺货、反证等关键块保留上游提供的摘要，再按增量 Token 成本升级全文。 | 27 个设计好的上下文场景中，关键证据保留率 **59.65%→100%**，关键证据以全文形式保留的比例 **59.65%→64.91%**。同一估算器下的超额计数 **4→0** 只属于内部一致性检查，不能作为独立收益证据。 | 估算等同于真实模型 tokenizer；真实模型绝不会超窗；摘要一定无损；当前配置等于实时读取模型窗口；该预算思想本身是首次提出。 |
| **3 工具调用决策**（Zheng Sitian） | 模型提出调用后直接执行，或只做单一权限检查。 | `tool-gate.ts` 在执行前依次核对读写权限、数据源状态、诊断指标范围、工具能力、前置条件与业务风险，输出执行／阻止／请求审批；数据适配器仍需再次校验店铺和 SKU 范围。 | 1,728 组确定性策略矩阵中，决策与预设策略一致率 **18.17%→100%**，三类决策宏平均召回率 **53.27%→100%**，按该策略定义的未经许可直接执行数 **1,273→0**。 | 该矩阵证明真实环境零越权；模型会自动选到最有价值工具；静态策略覆盖所有业务风险；多级门控为学术首创。 |
| **4 多源证据原因排序**（Li Yiheng） | 固定优先级规则按缺货、流量、转化、价格／促销输出触发的候选，不做证据评分。 | `ranking.ts` 分别提取缺货、流量、订单／访客转化、价格与促销的时段变化；按支持强度、数据质量、时序匹配加分，按反证扣分；保留缺失指标与观测 ID；识别“流量先降、后续缺货加重”的两阶段情形。 | 原预留但现已用于调试的合成集：单原因 24 例 Top-1 **18/24→24/24**；6 个双原因案例中，两种方法的 Top-2 均覆盖 **12/12** 个标签，未显示混因召回增益。 | 分数是已校准概率或已证明的因果效应；这组由同一项目生成的合成样例代表真实电商数据；三种评分组件各自已被主集证明有效；当前混因指标有增益。 |
| **5 结论核验与定向补查**（Li Zhen） | 全量数据直接输出排序第一项；查询成本另与固定次序加同一核验器比较。 | `verification.ts` 检查销售下降是否真实存在、候选原因的支持／反证／缺失、质量与日期覆盖；对转化下降补查价格促销，对销量降幅超流量降幅的情形补查库存；按缺口价值与查询成本建议下一指标，并避免重复查询。 | 同一合成集 36 例中，相对全量直接断言的决策正确率 **30/36→36/36**，错误强结论 **6/36→0**；相对固定顺序加同一核验器，平均查询指标数为 **3.67→3.67**，未显示调用量收益。 | 相对固定次序提高了决策正确率（两者在该集均为 36/36）；当前样本证明查询次数更少；混因第二原因也被独立核验；核验结果等于真实因果确认。 |

## 当前实验尚未覆盖的关键问题

1. **模块 4 的消融没有证明三个组件各自带来增益。** 在合成主集的单原因 Top-1 上，完整方法与分别关闭时序、质量、反证后的结果均为 **1.0**。这意味着主集的样例太容易或指标太粗，不能写“时序／质量／反证分别提高了准确率”。定向单元测试只证明这些开关会改变分数与局部判断，尚不是总体收益证据。
2. 已加入独立手写的 `eval/stress.ts` 压力案例，可检查时序、质量与反证的敏感性；但其结果也已用于调试，**不能再当作未接触的最终盲测**。下一轮应由不参与评分规则开发的人先固定新案例与标注，涵盖缺货晚于首次销量下降且没有二次下降、有二次下降的后发缺货、同日库存多源冲突、记录过期、缺失与查询失败、流量和转化同时变化、促销结束引发转化下降、销量与流量降幅不匹配。报告分场景的 Top-1、混因 Top-2、证据引用正确率及弃权／无依据结论原始计数，再做三项消融。不能用与 `ranking.ts` 同一评分公式造数并反过来证明该公式。
3. **模块 5 需要更强的查询选择测试。** 固定次序在现有 36 例上也达到 36/36，且当前两种方法平均查询数同为约 3.67，不能据此主张调用量收益。每类情景预先各取 1 例、限制最多 1 或 2 次补查的探索性探针中，双方正确率与查询数也相同；这些已接触的例子不算独立验证。当前回归测试增加了同日冲突、低质量竞争证据、稀疏日期覆盖的安全处理，但当库存来源已经相互矛盾且没有第三个独立来源时，系统只能保留“证据不足”，不能声称已自动解决冲突。下一轮应加入某源不可用、多个候选得分相近、每项查询成本不同、同一查询重复失败等情形；由独立标注给出“可接受的下一查询集合”，比较正确且有证据的结论数、无依据强结论数、弃权数、调用数和时延。只报告错误率会奖励一律弃权，必须同时报告覆盖率。
4. **模块 1～3 的实验仍是机制验证。** 模块 1 只用一张 5 节点 DAG，并以固定任务耗时、两组严重度和注入的最终核验故障模拟；“严重度不准确”组是在检查第一轮结果后追加的探索性压力场景，48 例合并均值按人为设定的两组等权计算，不能当作真实场景的期望收益。模拟已与当前执行器的整批等待语义一致，但没有测实际 Agent 工作流耗时。执行器虽支持完成后用 `verdict` 指定失败节点，当前 `diagnoseWithTools` 未传入该回调；集成流程的局部修复只在任务抛错时触发，最终诊断为证据不足时执行的是定向补查而非重跑。模块 2 的 27 个项目设计场景由项目代码选择重要类别，摘要保真性未单独核验；“0 次代理超额”由选择算法自身的估算器保证，需用实际模型 tokenizer 或接口用量独立核对，也需测真实回答的证据引用质量。模块 3 的 1,728 组合里 **1,698 个**预设标签为“阻止”，故同时报告宏平均召回率；标签按与实现同源的策略契约设定，100% 是契约一致性结果；其中写操作和高风险请求只在策略评测出现，当前诊断 Agent 的工具调用为 `safe` 模式、只读且固定低风险。需增加独立设计的越权、源状态变化和店铺／SKU 越界案例。真实源适配器与人工审批流程也应单独验证。
