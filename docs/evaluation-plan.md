# 五模块实验方案与可信度边界

本方案参照 [NeurIPS Paper Checklist](https://neurips.cc/public/guides/PaperChecklist) 对基线、实验细节、误差范围和复现材料的要求。目标是检验“相对普通 Agent/固定规则的改进是否在本项目任务中有效”。实验结果不自动证明学术首创或真实经营因果关系。

## 实验对象与冻结规则

- 任务：单店单 SKU，比较连续 7 天基线与 7 天异常期；指标为销量、支付订单、访客、库存、价格、促销。
- 核心合成案例：6 类情景 × 8 个变体 = 48 例；每类前 2 例用于初期开发，后 6 例共 36 例用于固定评测。单原因 24 例、混因 6 例、信息不足 6 例。代码字段仍叫 `holdout`，但这 36 例已被用于集成调试，不能再称为完全未接触的盲测。
- 金标准仅由数据生成器/评测器持有。Agent 核心只收到案例标识、时间窗和只读查询接口；查询返回值不含原因标签，案例和观测 ID 也不含场景名。ID 是可复现的哈希，并不能使同源合成数据变成独立盲测。
- 同一对照使用相同案例、指标定义和查询结果。模块 5 的**决策基线**读完全部 6 项指标后直接断言首位原因；**查询成本基线**使用同一核验器和最多 6 项指标，但按固定顺序查询。两组基线的数据预算与目的不同，必须分开解释。固定种子、代码哈希、Node 版本与逐例结果写入 `eval/results/latest.json`。
- 保留失败例，不删除。当前已根据固定评测/压力结果修复过实现，应记录版本变化；只有在另建未见案例并冻结最终源码后，才能声称新的盲测结果。
- 目前无真实业务数据，合成变体之间存在同一生成机制的相关性；配对区间只描述这批合成案例的波动，不能外推真实店铺。

## 对照与指标

| 模块 | 普通基线 | 本项目方法 | 独立消融 | 主指标与次指标 |
| --- | --- | --- | --- | --- |
| 1 任务调度/局部修复 | 串行执行、失败后全量重跑；另设并行 FIFO 作较强基线 | DAG 约束下按异常程度/下游影响选就绪节点，失败仅重跑受影响节点 | 关优先级；关局部修复 | 模拟完成时间（virtual ms）、重跑节点数、依赖违例数、被保留任务数 |
| 2 动态上下文预算 | 固定字符/4 估算与先到先得截断；另设固定阈值基线 | 密集内容修正估算，关键证据摘要优先，剩余预算升级全文 | 关密度修正；关业务重要性 | 关键证据保留率、估算预算超额率、遗漏反证数、摘要事实一致性 |
| 3 工具调用决策 | 模型提议即执行或仅按权限模式判断 | 权限→来源状态→指标范围→前置条件→业务风险的门控 | 去来源状态；去业务风险；去前置条件 | 决策准确率、未授权执行次数、误阻断率、审批召回率 |
| 4 原因排序 | 固定优先级规则：缺货→流量→转化→价格/促销；触发多个规则时依序输出多个候选 | 多源时序、质量、反证共同评分并给出证据 ID | 去时序；去质量；去反证 | 单原因 Top-1、混因 Top-2 召回、证据可追溯率 |
| 5 结论核验/定向补查 | 全量数据直接取 Top-1 不核验；固定顺序加同一核验器作查询成本基线 | 证据缺口/冲突/替代解释核验，按判别价值和查询成本选择下一项 | 无核验；固定顺序；无冲突检查 | 首位原因决策正确率、错误强结论率、信息不足保留判断率、每例平均查询指标数 |

模块 1 的时间是模拟工时，不能写成生产环境时延。模块 2 的“超额”按启发式或代理计数定义，**没有真实模型 tokenizer 时不能写成真实上下文溢出率**。模块 3 的政策准确率来自穷举/预设规则，不能写成用户真实审批质量。

## 指标定义

- Top-1 准确率 = 单原因案例中第一候选命中人工/情景标签的例数 ÷ 单原因案例数；混因单独统计，不把“命中任一原因”与“识别全部原因”混淆。
- Top-2 召回率 = 混因案例中真实原因落入前两名的个数 ÷ 真实原因总数；固定规则和本项目排序器都允许输出前两名。
- 模块 5 的“决策正确”在单因案例要求 `supported` 且首位命中，在信息不足案例要求不返回 `supported`；混因案例只要求 `supported` 的首位命中**任一**标签。它没有核验第二原因，不能称为“混因完整诊断正确率”。
- 错误强结论率 = 在所有案例中，系统返回 `supported` 但首位原因不在标签中或本应保留判断的比例。`needs_data` / `insufficient` 不是强结论。
- 关键证据保留率 = 进入预算的预先标记关键事实 ID 数 ÷ 所有关键事实 ID 数。仅统计事实保留，不把压缩后文本长度当准确率。
- 工具门控“准确”以手工规定的政策 oracle 为准，同时给出执行/阻止/审批三类混淆矩阵和误阻断，不只报总准确率。
- 查询成本按**指标查询次数**计，初查也包含在内，不含网络往返或真实费用；可在接入真实 API 后补充延迟和费用。
- 差值区间用固定种子、按案例配对重采样的 bootstrap 95% 分位数区间；样本小、情景非独立时不把它解释为总体显著性。

## 当前合成主集读数的解释

- 模块 4：单因 Top-1 为固定规则 0.75、本项目排序 1.00（24 例）；混因 Top-2 两者均为 1.00（6 例）。去时序、去质量、去反证后的单因 Top-1 均为 1.00，所以本主集**没有证明**这三个组件各自提升 Top-1；压力题只说明机制会响应指定边界条件。
- 模块 5：全量数据直接断言首位的决策正确率 0.8333、本项目核验 1.00，错误强结论率 0.1667→0（36 例）。固定顺序加同一核验器的决策正确率也是 1.00，平均查询指标数与定向补查均为 3.6667。故当前主集支持核验相对无核验的安全收益，**尚未显示定向补查相对固定顺序的成本或准确率收益**。
- 另对每类情景预先取变体 2 各 1 例，在总查询上限 3 项或 4 项下比较固定顺序与定向补查。两种上限下，双方决策正确率均为 0.6667，平均查询数分别同为 2.8333 和 3.1667。这个 6 例探索性预算探针也没有显示定向补查收益；它不是新增盲测或独立业务样本。
- 这些是同一生成器的相关变体，且原评测集已用于调试。结果只表明当前合成任务的表现；规则阈值、场景难度和独立业务案例仍需另行验证。

## 可靠性检查

1. **数据完整性**：跨店铺/SKU/窗口记录拒绝；`missing` 与真实 `0` 区分；来源、抓取时间与更新时间保存；计算均值时按同一指标定义。核验阶段要求被使用的趋势指标在每个窗口至少覆盖半数日期，避免 7 天窗口仅凭 1 天观测支持结论；这个覆盖阈值仍是待校准的启发式规则。
2. **负例与混因**：包含流量先降、随后缺货，促销结束引起转化下降，价格晚于销量下降，冲突库存，缺失流量等情景。保留反证及无法判断的输出。
3. **消融解释**：同一主集的 Top-1 若在去时序/质量/反证后仍不变，必须如实写“主集未检验出该组件对 Top-1 的贡献”；再用单因素压力情景检验机制敏感性，但不把定制压力情景算进主集准确率。
4. **审计材料**：保存数据生成代码、案例级 CSV、参数/阈值、代码哈希、Node 版本、失败日志和运行命令；任何后续修复单独注明。
5. **真实数据扩展**：选取授权的匿名 SKU 历史案例，由不知算法输出的业务人员独立标注“可支持的可能原因、不可判断、需要补查的指标”，至少报告标注分歧，再跑同样基线和消融。真实经营干预需要额外因果验证，不由本项目的关联评分替代。

运行：`npm test`、`npm run eval`。可视化：`npm run dev` 后看实验页；原始逐例结果在 `eval/results/case-results.csv`。全部实验数据均显著标记为合成数据。
