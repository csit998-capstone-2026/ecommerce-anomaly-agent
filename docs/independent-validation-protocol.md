# 独立验证与答辩材料准备

当前仓库的 48 个合成案例、36 个固定评测案例和手写压力案例都已参与开发调试；它们适合回归测试，不是未接触的盲测。下列流程用于下一轮验证，**尚未执行**。

## 先冻结，再拿新案例

1. 记录 Git 提交、`eval/results/latest.json` 的源码哈希、阈值、随机种子和预定主指标。冻结后只允许修复不影响评分规则的运行错误；若改评分规则，必须重新选独立案例。
2. 由未编写排序与核验规则的成员收集至少 30 个新案例。最好是获得授权后脱敏的历史经营记录；没有真实数据时，由独立成员按业务故事手工设计并标注，明确写作“独立构造案例”，不能称为真实店铺验证。
3. 覆盖缺货、流量下降、转化下降、价格/促销变化、双原因、信息不足六类，每类至少 5 例。另加同日冲突、缺失、过期、来源不可用、销量下降时间先于候选原因、连续 7 天中只有少量有效记录等边界。不要复制现有生成器参数或其数据模式。
4. 案例 ID、来源 ID、文件名不能透露原因；Agent 只收到 `diagnosisCase` 与按指标返回的观测。标注文件单独保存，不送入数据工具或提示词。

## 标注规则

- 两位标注者独立阅读同一时间窗的销量、访客、订单、库存、价格和促销记录，分别给出：`可支持的原因集合`、`是否足以形成较强结论`、`下一步可接受的补查指标集合`、`最关键的原始观测 ID`。
- 标注者可以选择“无法判断”；混合原因允许多标签，并记录先发生原因与后续加重因素。若两人不同意，保留原始分歧，第三人复核形成用于评分的共识标签；报告原始一致率与分歧例数。
- “价格上涨与销量下降同时出现”只能标为可能解释。缺少干预或外部控制时，不标“已经证实价格导致下降”。
- 标注模板列：`caseId,annotatorId,causes,decisionSupported,acceptableNextMetrics,keyObservationIds,notes`；`causes` 与多值字段用 `|` 分隔。个人身份和店铺敏感信息不进入仓库。

## 预先固定的比较

| 模块 | 主要对照 | 主指标 | 必报的风险/成本 |
| --- | --- | --- | --- |
| 1 调度/修复 | 并行 FIFO + 全图重做、FIFO + 局部修复 | 同一故障轨迹下实际完成时间及执行节点数 | 长尾时延、优先级造成的饥饿、失败节点未修复 |
| 2 上下文预算 | 固定字符估计 + 先进先出、仅密度估计 | 真实 tokenizer 计数下的关键事实保留率 | 真正超窗次数、摘要事实错误、输出证据引用正确率 |
| 3 工具门控 | 仅权限检查 | 三类决策宏平均召回率 | 越权执行、误阻断、审批请求数和处理时延 |
| 4 原因排序 | 固定顺序、去时序、去质量、去反证 | 单原因 Top-1 与混因 Top-2 召回 | 错误强排序、证据引用正确率、分场景结果 |
| 5 核验/补查 | 不核验、固定顺序补查 | 有证据支持的正确结论率 | 无依据强结论率、弃权率、平均调用数、不可用来源下表现 |

所有方法在同一案例、同一数据快照、同一调用上限下配对运行。报告分子/分母和逐例失败，不只报百分比。对按案例成对的差值提供 95% bootstrap 区间；样本少时把区间视为不确定性描述，不写统计显著性结论。若模块 4 的消融仍与完整方法同分，或模块 5 的固定顺序仍同样正确，应如实记录“该实验未显示额外收益”。

## 复现包

保存脱敏案例版本、独立标注原件、共识标签、源码提交、命令、Node 版本、`case-results.csv`、失败案例和人工更正日志。实际店铺数据不得提交到公开仓库；可在许可范围内提供匿名统计、字段规范和可运行的合成替代集。
